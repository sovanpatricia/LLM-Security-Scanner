## Summary

Most of the meeting was about data. We agreed that the team builds its own dataset. We also
discussed where the scanner could be used, from a SonarQube-style tool to support for coding
agents, and which threats to focus on.

## Discussion

### 1. Dataset

- We build our own dataset ("set de date făcut de noi"): we found no public, labelled dataset
  of vulnerabilities in code that integrates LLMs.

### 2. Reference tool

- SonarQube was mentioned as an example of the kind of tool we aim for: static analysis that
  points the programmer to risky code. It is a suggestion for the shape of the product, not a
  tool we must build on.

### 3. Possible uses of the scanner

1. **Coding agents:** give the agent extra context for validation and security of the code it
   writes.
2. **GitHub agent:** run on the repository and leave a pop-up (a comment or a warning) listing
   the threats it found.
3. **Research:** identify the most common threats in LLM-integrated code, to decide what the
   scanner should detect first.
4. **Integration into a coding agent:** the recommended direction.

## Scope

- Vulnerabilities in **Python code that uses an LLM**, mapped to the OWASP Top 10 for LLM
  Applications.
- A tool for the programmer, such as a VS Code extension, with a demo on real-life code.
